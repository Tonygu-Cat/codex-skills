# 任务书 · 结构规格

结构与顺序固定：「已确认决定、实现假设与待确认事项」放最前（领导发出前核对边界），「交付终点与授权」紧跟「规矩」，「完成条件」放最后（收拢约定结果与证据）。整本 ≤4000 字符，单任务的书通常 1500–2000。本规格不配样文——照规格自己写，措辞贴合当下的任务，别套任何现成句式。

## 开头（不带标题，五件事各一句）

- 你是执行者，按用户要求、约束及已有授权执行；这份任务书是对要求的解释，服从用户后续修正。遇到事实冲突或新的重要边界可请求决定，只暂停受影响工作；真正阻塞写进 `BLOCKED.md`，普通实现细节自主处理
- 断了、换新会话：先读进度记录接着做，别重做；每做完一项立刻更新。执行端已加载 context-handoff 时，进度记录就是它的交接文档，不另建 `PROGRESS.md`；否则用 `PROGRESS.md`
- 这活为什么干：一句意图，为什么干＋干完世界什么样——书里没写到的普通实现细节，执行者在原范围内自主处理；不能据此扩大目标
- 两个要求打架时的让步顺序（如「算得对 > 做得全 > 做得快」）
- 死规矩与参考的分界：「只允许」「不许」违反算失败；「建议」有更好的路就走，在进度记录里记一句为什么

## 已确认决定、实现假设与待确认事项

分别列出已确认决定及授权依据、范围内可自主执行的普通实现假设及其依据、需要用户批准的重要待确认事项。重要选择未获回复不执行，只暂停受影响工作；已有授权不重复询问。没有对应事项时写「无」，不为填满格式制造决定。
写不出机器可判命令的目标（文风、体验类）采用有依据的抽查点或用户确认方式，注明所需证据，不强造数字。

## 界限

- 白名单：只允许改哪些路径＋新建文件，其余只读——用白名单不用黑名单，黑名单永远列不全
- 不得降低或绕过既有验收（测试、验收脚本、CI 配置）；原需求所需测试和注册变更须直接服务已确认目标、有具体因果证据、没有更小合理方案且不突破明确禁区。既有门禁不能单独证明新功能必要，也不能用自行新增的要求为额外开发作证。对明确只读文件，无 git 时记录完整 sha256 指纹并核对未变
- 点名最诱人的顺手活（那个一行就能修的无关 bug、顺手重构、顺手装工具），未授权不做，普通建议交付时简述；确实阻塞原目标的事项才写 `BLOCKED.md`。未经授权的不可逆操作（删数据、改权限）暂停该部分并请求决定，不受影响工作继续

## 现状与任务 0

- 实测数字逐条带来源与日期，查不到的标「猜的，没验证」；能提前实证的关键结论（如「只改实现就能全绿」）写进来，提前拆掉借口
- 执行型按交付范围实测当前工作分支、相关本地检查和适用必需 CI；仅当已授权交付包含发布，或改动直接涉及相关路径时，调查目标分支、分支保护/PR 要求、生产部署入口、线上版本识别、冒烟检查与回滚办法；调查本身不授予执行权限
- 会改可运行代码、配置、schema、迁移或发布路径时，同时实测 DeepHarness（本机 DeepSeek Harness/DSH）的真实入口、独立新会话如何访问仓库、审查记录如何绑定 base/head SHA；不能调用就记为受该门禁约束的交付步骤前的阻塞，禁止编命令；审查不授予提交、推送或发布权限
- 任务 0：跑已核实的指定命令，核对相关事实、基线及授权范围内的交付路径；不存在的必需命令、空转的假检查、当前终点缺失的权限才记 `BLOCKED.md`；前提不符只暂停受影响工作，附证据继续不受影响部分；核对无误后把「理解的目标／顺序／最大风险」≤10 行写进进度记录再动工

## 任务 N

每个任务包含：一句话目标带有依据的可验证结果，合理量化时才写数字；从哪下手一句（多任务按依赖排序，说清为什么它排前面）；死规矩写成「做 A，否则 B」并带具体后果；验收＝实际检查命令及判定，或适合该目标的可核验产物（机器检查含适用的防漏判定，如「无新增跳过」）；反向验证＝故意制造一次失败、贴变红输出、还原后贴全绿——凡是「坏了没人会知道」的检查都要这一步。

## 规矩

- 防作弊点名到具体姿势：以伪造达标为目的跳过测试（skip/todo）、放宽判断、把被测对象换成假的（mock）、删测试、降低阈值或绕过验收脚本、`|| true`（失败也当成功）——全算失败；测试数／覆盖率只许 ≥ 基线。必要测试与注册变更按上述范围判据处理，不降低或绕过既有验收。仅补测试且明确禁止改实现的任务，加「实现目录 `git diff` 为空（业务代码一行没动）」
- 未经授权不增加流程、权限、依赖；确为必要配套时按范围判据和明确禁区处理，重要范围变化实施前确认。仅真正阻塞的未决事项写 `BLOCKED.md`，未实施建议不是必做清单
- 同一条验收连败 3 次先重新诊断方法与前提，再决定安全重试或报告阻塞；发现回归只撤回本次相关变更，保护用户及其他任务的修改并如实报告；未达约定结果须记为未完成，诚实报告不替代完成证据
- 项目自有纪律（分支／PR 规则、提交前检查）写在这里

## DeepHarness 独立验收

会改运行态的执行型任务必须带本节；纯文档、纯探索或实证无可运行产物时可标「不适用」并给证据。按 [deepharness-review.md](deepharness-review.md) 只写与本次风险有关的测试，别把清单全抄进任务书。

- 作者完成实现和适用全量检查后，按已有授权准备可核验的送审版本，记录 base SHA 与待审 head SHA；提交或推送仅在已授权时执行，审查若依赖未授权步骤须说明并请求决定；DeepHarness 用没有参与实现、没有继承作者结论的全新会话审查最终 diff，并独立复跑检查和风险回归
- reviewer 只读审查，不修代码、不改判卷标准、不替作者补证据；报告必须列会话标识、时间、base/head SHA、实际命令与退出码、发现和 `PASS`/`FAIL`。有问题由作者修，任何代码变化或 base 前移都让旧报告失效
- 只测本次改动实际改变的属性：改了发送、去重、重试或消费逻辑，才测重复发送、误去重、重试、并发和重放；改了跨版本共享的数据格式、schema 或配置，且部署确实会新旧版本并存，才测升级和兼容窗口。只是经过这些路径（改文案、改无关字段）不触发。被改变的属性没有可判测试才算 `FAIL`，由作者补后再重审；不适用的项在报告里写一句原因即可
- DeepHarness 无真实入口、无法访问 exact SHA、测试失败或存在未关闭的高风险发现，一律写 `BLOCKED.md` 并停在受该门禁约束的交付步骤前；可在其中附可直接粘贴的审查提示词，但不得降级成执行者自批

## 交付终点与授权

交付终点：根据本次要求及已有授权填写。
授权依据：对应的用户要求或明确的持续授权。
必要验证：为达到该终点需完成的相关检查和适用的既有必需门禁。
完成证据：与该终点对应的实际结果。
未授权步骤：不写入必做清单；无需为暂未需要的后续步骤索要批准。

本地修复止于修复和必要验证，方案任务止于方案。下面的提交、合并与上线步骤仅在当前交付授权包含对应动作时采用；已经明确授权上线则完整保留适用步骤，不重复索权。审查要求不扩大操作权限，也不得借范围规则降低适用门禁。

- **全量测试**：列出仓库要求的全部本地检查与必需 CI；全部成功、无取消/运行中、无新增跳过，且工作区只含白名单改动，才能继续
- **提交与送审**：提交并推送工作分支，记录工作提交 SHA、PR 链接/编号和当时的目标分支 base SHA；拿到绑定 exact base/head SHA 的 DeepHarness `PASS` 后才可继续
- **合并**：确认送审后代码与 base 都没变，再按仓库现有 PR/保护规则合并到实测得到的目标分支；任何 SHA 变化先重跑全量检查与 DeepHarness 审查。禁止直推绕保护、强推、管理员跳过检查；记录合并 SHA
- **生产部署**：只从合并后的 SHA 或其不可变构建产物走仓库已有正式发布流程；禁止拿合并前分支直接上线。记录部署命令或流水线、部署 ID、环境、时间和版本
- **线上验证**：用版本端点/构建信息证明生产运行的是合并 SHA，再跑关键冒烟与健康检查并观察仓库规定的窗口。异常时按既有回滚流程恢复上一稳定版本，贴回滚与恢复证据，任务仍记未完成
- 当前授权终点遇到缺权限、待人工审批、合并冲突、生产检查失败时才写 `BLOCKED.md`，仅暂停受影响工作；不得把「已提 PR」「已触发部署」冒充「已合并上线」

## 完成条件

- 按用户明确目标和约束列有依据的验收结果，不凑条数、不新增业务指标；结果、必要验证和范围约束均要有相应证据
- 完成证据与授权终点一致：本地修复给实际差异和相关检查结果，方案给可核验的方案产物。已授权合并上线时，才要求适用全量本地检查和必需 CI 全部成功、工作提交已合并目标分支、生产版本等于合并 SHA；部分授权只列对应证据并引用依据
- 会改运行态时再加独立验收硬指标：DeepHarness 报告为 `PASS`，绑定最终 base/head SHA，无未关闭高风险发现；报告后被审 head 内容变化为 0；已授权合并时，合并时目标 base 仍等于报告值
- 每条给出实际命令输出或产物证据；适用时附反向验证的红→绿证据和 DeepHarness 审查凭据。只说做完了不算，不为填证据增加未授权步骤
- 交付说明需求对应变化、必要配套依据、实际验证结果及未实施建议；没有配套或建议时写「无」。有真实阻塞时附 `BLOCKED.md`；不把建议变成阻塞或必做项
- 完成即停止，不自动追加优化或新目标。「继续完成原任务」只处理原有剩余项；已经完成则说明完成。约定时间或轮次止损只触发如实报告，不把未达到的完成条件判为通过

## 探索型：改四处，其余同款

领导要的是答案本身（调研、选型、「该不该做 X」）时，硬指标只会换来凑数的答案：

1. 完成条件换成学习目标：结论条数设上限、每条附来源与日期或可复跑的复现步骤——宁收 2 条实的，不收 10 条凑的
2. 预算换成可承受损失：最多烧多少时间／查多少来源，烧完就交卷，交「目前最优＋还没排除什么」
3. 防作弊主防编造：凑数的结论、查无此文的引用、没跑过的「实测」都算作弊；每条结论要经得起领导随机抽一条、10 分钟内复现
4. 此路不通＝合格交付：带证据证明某方向是死路（死因＋原始输出），按完成计

探索结论本身不合并、不部署；只有用户已授权落地时才安排后续执行型目标，并沿用已有授权；类型变化不增加提交、合并或部署权限。「仅生成方案」到方案交付即停止。
