# 持续检查点＋保留现有拦截

仅在用户明确选择这一阶段模式时采用；记录适用项目/任务、授权原话和证据边界。它接受现有拦截可能失效的残余风险，不代表用户主动授权压缩，也不满足严格“零压缩”。其他仍要求严格不压缩的任务不自动降级。

## 执行规则

- 沿用唯一 CURRENT_HANDOFF.md，不另建第二份主交接。持续指工作中的事件驱动落盘，不是定时后台服务，不需要每个无状态查询都写一次。
- 用户改变目标、约束或授权后，在下一个有副作用的工作单元前更新；代码/配置修改、验证结果、关键调查结论或阻塞变化后，在下一个工作单元前更新。
- 每轮有实质变化的最终回复前，以及等待外部结果、委派、切换阶段或开始可能大量输出的操作前，补齐尚未记录的事实。可把同一个不可分割操作及其紧随验证合并为一个工作单元，不能把整段长任务当成一个单元。
- 检查点写完后，最终回复仍按主 Skill 的“推进契约”收尾：以“下一步”“用户操作”结束，需要批准时附可直接发送的回复原文，并与交接中的 Next exact actions 一致。“交接已同步”至多一行，不作为最后一句。
- 每次至少记录：项目/任务及当前所有者、revision、覆盖到的最后材料事件、目标与约束、源分支/提交、已完成/未完成、必要工件路径与保存状态、验证证据、权限/阻塞、下一步。记录已观察的事实；未知的外部状态和检查点覆盖缺口标为未验证。
- 更新当前段落，必要历史保留在决策/修订记录；不要不断向当前状态叠加相互冲突的“下一步”，也不要抄录长聊天或日志。明确路径和证据引用优于把所有内容再次灌入上下文。
- 每个检查点逐文件回读并运行已有 validate_handoff.py；结构 PASS 不证明事实完整。写入/校验失败时，保留上一个有效检查点，在下一个实质工作单元前停止并报告，不能标为已保存。
- GitHub 同步沿用主 Skill 的授权与目标规则：仅向已核验且已授权的仓库/分支同步，远端回读后才报告已同步。没有目标或同步失败时，明确区分本地已保存与远端未同步；必要发布失败仍阻塞换代/归档。
- 未提交代码仍保留在原工作区；只记 hash 不算保全。不得为了检查点擅自 commit、stash、丢弃或上传代码。换到新工作树前按原换代协议确认必要工件实际可读。

## 现有拦截如何处理

保留已登记的 PreCompact 脚本、注册范围、同步设置和正常信任；本模式不新增登记、不改参数/阈值、不重新信任、不关闭已有 Stop/提醒，也不增加后台进程、宿主补丁或第三方依赖。若需要这些变更，另按精确范围部署。

将状态分开报告：文件存在/指纹匹配、登记存在、历史信任证据、当前宿主加载、实际事件拦截。旧 CLI 的成功不能证明当前桌面任务已加载；未登记的任务没有因为读取本 Skill 而获得拦截保护。配置漂移先记录核对，不能恢复成旧整份配置来追求旧 hash。

正常拦截后停止该任务业务，说明最新有效检查点及覆盖缺口，给出用户下一步的确切操作和可直接回复的确认原文，进入用户确认的交接边界；不重复发送“继续”，不移除拦截来挤出一轮总结，不把用户确认交接解读为允许压缩。后续换代仍走 manual-confirmation.md 与 task-rollover.md 的保全、唯一继任和接手核验流程；本模式本身不创建或归档任务。

## 意外压缩后的恢复

先读取唯一交接并核对最新用户指令、项目/当前 owner、分支/提交、脏工件和未完成动作；记录为降级事件，不声称拦截成功或保证没有遗漏。不盲目重试可能已完成的外部副作用。

权限和工作状态可核验且用户本来允许业务继续时，才从记录的下一步继续；存在未知副作用、所有权冲突、工件缺失或原任务仍暂停时，保持暂停并只做获准的核对；保持暂停时同样按推进契约说明下一步由谁执行、用户要做什么。本模式不解除既有业务暂停/审批，不需要因压缩重复首次任务运营询问。

## 验证与生效范围

本次仅修改规则时，验证 Skill 格式/链接、检查点结构和前后受保护文件指纹即可；不主动触发真实压缩或故障注入来“证明”持续检查点。规则读取生效与宿主钩子生效分别说明。

已运行的其他任务不会因磁盘更新被证明已读新版；跨任务通知、批量推广和运行时重载必须在授权范围内进行。严格失效安全和完整自动换代保留为后续目标，不把本阶段完成标成它们已验收。
