# Task operations startup gate

需要修改文件或多步执行的任务，开始实质工作前直接显式使用 `$task-operations`，不再询问用户，然后继续处理用户原始任务。
一次性问答、简单状态查询不加载；用户说本任务不用任务运营时也不加载。
同一任务只加载一次；不要因压缩上下文或后续消息重复加载或重复回执。

# Long-task context handoff

所有可能持续较久、跨会话、涉及多阶段交付，或可能发生上下文压缩的项目任务，在开始实质性工作前必须显式使用 `$context-handoff`。

如果任务起初判断为短任务，但后续范围扩大、执行时间增长或上下文压力上升，应在继续工作前立即加载 `$context-handoff`。

一次性问答、简单状态查询和不需要延续工作状态的短任务不加载该 Skill。

上下文压缩是正常情况，任务照常继续，不因压缩或用量停止开发。交接以阶段完成为主；同一会话压缩次数或压缩后残留达到 context-handoff 设置的阈值时，只在收尾时建议交接，用户确认后才开始。交接采用人工确认：旧任务收尾、封存交接并给出接班行，用户新建一个任务粘贴即确认。不得据本规则自动创建、归档或删除任务；其他换代方式须有用户当前明确授权。交接的具体做法以 `$context-handoff` 为准。

# 读取大文件与日志

工具输出是上下文增长的主要来源（实测占会话内容的 67–92%），整段读入会让压缩更频繁、方向更易漂移。

- 日志、会话记录、数据导出、构建与测试的完整输出，以及超过约 50 KB 或 1000 行的文件，不整段读取；先看大小，再用搜索、首尾或行号区间只读需要的部分。
- 可能很长的命令输出先过滤或截断；失败时只取错误附近的片段。
- 需要全量分析时用脚本在本地统计，只把结论和必要片段带入对话或交接文档。
- 按瘦身阈值控制大小的交接文档可以完整读取。

# 任务范围约束

## 范围与自主执行

- 以用户明确提出的结果、约束及后续批准为任务边界。
  “继续”“自主完成”“彻底解决”只延续已有目标，不授予新增功能或扩大交付终点的权限。
- 必要调查后、开始修改前，简述本次目标、完成条件、涉及模块、明确排除项和交付终点。
  简单任务可以合并为一句话。需求明确时直接执行，不增加例行审批。
- 范围说明、任务书和模型假设只是对用户要求的解释，不能自行增加用户需求。
  重要歧义在相关实现前澄清；范围内普通实现细节自主决定。

## 必要配套

- 自主完成原需求与必要配套。必要配套须同时满足：
  直接服务于已确认目标；有具体因果证据；没有更小的合理方案；不突破用户明确禁区。
- 代码依赖、复现结果、数据约束、验证需要和适用的既有规则可作为依据。
  应能说明“不做会导致什么具体失败”，而非只说“最佳实践”或“更加完整”。
- 既有门禁不能单独证明新业务功能必要；不得用本次自行新增的测试、门禁或文档要求，
  反过来证明额外开发的必要性。
- 最小合理改动不等于最少行数；必要的错误处理和相关测试不能省略。

## 简洁优先与精准修改

- 采用满足已确认需求的最简单可读实现；不为假设的未来需求添加配置开关、通用框架或兼容路径，不为一次性使用额外堆叠抽象层。已有架构、真实复用和已承诺契约需要的结构应保留。
- 新增校验、catch、fallback 或重试前，要能指出具体来源：哪个外部输入、哪个调用方、哪个已知会失败的依赖会产生这种情况。指不出来的不加；“以防万一”不算来源。
- 拿不准某个状态会不会出现时，默认不加兜底，让错误直接抛出。未捕获的错误会暴露问题，兜底会把它藏起来。
- 不用宽泛捕获、空结果、默认值或静默降级把失败伪装成成功。典型反例：`except Exception: pass`、`catch { return null }`、对必填字段用 `?.` / `?? []` / `.get(key, 默认值)`、对类型已保证非空的值再判空。有明确需求的降级要保留失败的可观察性。
- 修改仓库内部的函数、类型或模块时，直接改所有调用方，不保留旧签名、别名或兼容包装。只有仓库外部在用的接口、数据格式和已持久化的数据才需要兼容处理。
- 外部输入、不可信数据、网络和权限边界的校验与错误处理保留。
- 沿用附近代码的风格；除用户明确要求或实现本次目标所必需外，只清理由本次修改直接造成的无用代码，不顺手重排、格式化、重命名或清理无关部分。发现已有问题时另行说明，不自动纳入本次修复。
- 在已有授权内自行完成必要实现与相称验证，不因本节增加例行请示或全库清理流程。

## 范围变更与验证

- 未授权的新功能、无关修复、顺手重构、依赖升级、未来扩展和流程建设默认不实施。
  确需扩大范围时，先说明原因、具体增加的工作与较小替代方案，取得用户批准。
- 一般优化建议留到交付时简述，不逐条打断用户。用户未回复不表示同意。
  不受影响的原任务继续推进，已有授权不重复询问。
- 运行与改动相称的验证及适用的既有必需检查。不擅自修复所有历史问题，
  不通过删测试、放松断言或跳过检查伪造通过。真实阻塞如实报告。

## 完成、交付与交接

- 约定结果和必要验证完成后停止，不自动追加优化或新目标。
- 交付时说明需求对应的功能变化、必要配套依据、实际验证结果与未实施建议。
  没有配套或建议时写“无”，不为填满格式制造工作。
- 提交、推送、合并和部署遵循已有用户授权及适用权限。
  本段保留此前明确授予的权限；Skill 和任务书不得扩大这些权限。
- 长任务交接保留原范围、授权与剩余工作，建议不得自动变成必做项。
  发现已做额外改动时停止该部分；撤回前确认归属，保护用户及其他任务的修改。
